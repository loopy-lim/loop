# 다른 개발 agent에서 Loop가 배울 점: Pi Lead·Herdr 후속 조사

- 확인일: 2026-09-27. 공식 문서와 프로젝트 소유자의 저장소만 사용했다. 외부 agent를 설치하거나 동일 과제로 속도를 비교하지 않았다.
- 질문은 모델 응답 시간이 아니라 **사용자 요청 → 요구가 반영된 코드 → 실행 검사 → 검토 가능한 결과**의 시간을 줄이는 방법이다.
- 기존 [개발 속도 비교](./2026-09-27-agent-development-velocity-comparison.md)를 보완한다. 아래의 `확인`은 외부 프로젝트의 문서화된 기능이고 `Loop 제안`은 설계 가설이다. 제품 간 성능 순위는 아니다.
- Pi의 공식 저장소 옛 주소 `badlogic/pi-mono`는 현재 아래에서 사용한 `earendil-works/pi`로 redirect된다. [저장소 redirect](https://github.com/badlogic/pi-mono), [현재 저장소](https://github.com/earendil-works/pi). Pi SDK 원문에서 steering은 현재 assistant turn과 그 도구 호출이 끝난 뒤 들어가며, follow-up은 실행이 멈출 때 들어간다고 확인했다. [SDK Prompting](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md). Extension의 도구·명령·TUI 표면도 해당 저장소의 [extensions 문서](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)에 있다.

## Loop 개선 후보: 우선순위와 검증법

현재 Loop는 `loop_run`이 owner 인계를 확인한 뒤 돌아오고, Pi Lead가 한 대화에서 상태·steer·작업 추가를 다루며, worker 탭은 종료 시 닫힌다. Rust graph는 scope·의존성을 검사하고, provider registry는 quota group을 사용하며, benchmark trace는 run event의 작업·검증·attention 수를 집계한다. [확장 코드](../../packages/pi-loop/src/extension.ts), [quota group](../../packages/providers/src/registry.ts), [trace](../../crates/loop-core/src/benchmark/trace.rs), [실행 검증](../findings/pi-lead-tui-development-flow-verification.md). Rust core의 requirement/check coverage와 failure policy 검사는 이미 HEAD에 있다. [graph validation](../../crates/loop-core/src/graph/validation.rs). Bridge 입력→generated protocol→Pi/TypeScript 소비자 연동은 현재 작업 트리의 **미커밋·미완성 작업**이므로 이를 완료된 사용자 경로로 보지 않는다. 아래는 기존 기능의 복제가 아니라 남은 간극을 위한 후보이다.

### P0 — 실제 개발 시간과 신뢰성에 직접 닿는 항목

1. **Steer 결과를 단계별로 보여 주기.** `요청 접수 → run 기록 → worker에게 전달 → worker가 확인 → 변경 검사 통과`를 분리한다. 앞선 실측에서 `guidance_delivered`가 있었지만 새 `#` 규칙은 코드에 반영되지 않았다. 새 허용 기준은 실행 가능한 검사와 의존 작업 또는 후속 run으로 연결한다. Pi와 OmO의 steering은 전달·재개 UX 참고 자료다. [Pi SDK](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md), [OmO task](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/senpi-task.md). **검증:** 실행 중 원문 지시를 보낸 fixture에서 각 단계의 event와 최종 코드/테스트를 대조한다.
2. **coverage 선언과 의미 검증을 연결하기.** Rust core는 작업 requirement마다 check coverage를 요구한다. Bridge/Pi 소비자 연동을 완성한 뒤에도 선언된 검사가 **정말 그 동작을 검사하는지**와 실행 중 새 기준이 coverage에 들어갔는지는 별개다. 성공 exit code나 worker의 `VERDICT`만으로 목표 달성을 선언하지 않는다. OmO는 worker의 완료 주장을 독립 gate/ledger로 확인한다. [orchestration](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/orchestration.md). **검증:** 형식상 coverage가 있지만 새 조건을 검사하지 않는 fixture가 검토 필요로 표시돼야 한다.
3. **최초 작업 시작의 형식 비용 줄이기.** 작은 수정은 단일 execution node·focused check로 곧바로 접수한다. Pi가 긴 JSON task spec을 매번 작성하는 시간을 재고, scope/contract는 유지하면서 자주 쓰는 필드의 안전한 기본값이나 typed builder를 bridge 경계에 둘지 판단한다. OmO의 빠른 직접 실행과 Aider의 기본 code 모드가 비교 기준이다. [OmO](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/orchestration.md), [Aider modes](https://aider.chat/docs/usage/modes.html). **검증:** 요청→`worker_started` 지연, 모델 turn 수, 생성 task 수를 같은 fixture로 비교한다.
4. **쿼터 그룹을 실행 동시성까지 확장할지 계측하기.** Loop는 실패 candidate 제외에 quota group을 이미 쓴다. 429 재시도 중 화면의 잠시 idle을 성공으로 해석하지 말고 terminal provider 결과까지 기다리는 검사도 있다. 남은 질문은 같은 Z.AI 인증의 병렬 호출을 얼마나 허용하면 전체 완료 시간이 가장 짧아지는지다. group별 동시성 제한이나 backoff 변경은 완료 시간·429·재시도 비용을 실측한 뒤 결정한다. [OpenHands concurrency warning](https://docs.openhands.dev/sdk/guides/parallel-tool-execution). **검증:** scripted 429와 실제 인증 실행을 분리하고, 명시되지 않은 provider로 자동 우회하지 않는다.
5. **기존 trace에 구간별 시간을 더하기.** `TraceSummary`의 event 수 집계를 출발점으로 `요청 → DAG 접수 → owner lease → 첫 worker 시작 → 첫 수정 → focused check → 전체 검증 → 사용자에게 결과 표시` 시각을 분리한다. 첫 수정 시각처럼 현재 event에 없는 값은 관측 기능을 넣기 전에는 추정하지 않는다. 모델 호출 수·토큰·재시도·attention·완료율을 함께 본다. [OpenHands tracing](https://docs.openhands.dev/sdk/guides/observability), [mini-SWE baseline](https://github.com/SWE-agent/mini-swe-agent/blob/main/README.md). **검증:** 동일한 4개 fixture를 이전 경로와 새 경로에서 반복하고 분포를 보고한다. 현재 실공급자 단일 작업의 약 20초는 향상률 근거가 아니다.

6. **실제 수정 경로와 선언한 `writeScope` 대조.** Rust graph의 scope 충돌 검사는 *선언*의 관계를 검사한다. writable worker가 실제로 바꾼 경로를 종료 후 선언 범위와 비교하는 경로는 이번 코드 조사에서 확인하지 못했다. worker 시작 전 dirty tree를 기록하고 worker별 diff/변경 파일을 귀속할 수 있을 때만 위반 여부를 판정한다. 동시에 다른 사용자가 수정한 파일은 worker 변경으로 추정하지 않는다. 범위 밖 변경이 확인되면 영수증과 함께 사용자 검토 대상으로 올리고 자동 reset은 하지 않는다. [Loop graph validation](../../crates/loop-core/src/graph/validation.rs), [OmO isolated child](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/senpi-task.md), [Claude worktree isolation](https://code.claude.com/docs/en/sub-agents). **검증:** 범위 안/밖 수정, 기존 dirty file, 병행 사용자 편집, worker 실패를 각각 재현해 누락·오귀속·데이터 손실이 없는지 확인한다.
7. **Pi worker의 구조화된 종료 신호 검토.** 현재 Herdr adapter는 `idle`을 본 뒤 transcript 마지막 줄의 정규식으로 `Retrying (N/M)`과 최종 실패를 구별한다. [현재 판정 코드](../../packages/providers/src/herdr-agent.ts). Pi SDK는 `agent_end` 뒤 자동 복구가 이어질 수 있고 `agent_settled`를 완전한 정착 신호로 설명한다. [Pi SDK events](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/sdk.md). **가설:** Herdr가 Pi의 구조화된 종료 event/receipt를 전달할 수 있다면 이를 주 판정으로 쓰고 현재 화면 regex는 fallback으로 둔다. Herdr API가 그 신호를 제공하는지 아직 확인하지 않았다. **검증:** 일시 idle→재시도→성공, 재시도 소진, 무출력 종료를 각기 구별한다.
8. **focused check 실패를 같은 worker에게 즉시 돌려주기.** [Aider](https://aider.chat/docs/usage/lint-test.html)는 편집 직후 lint/test를 실행하고 실패를 같은 대화에서 수정한다. 현재 Loop의 [task execution](../../packages/orchestrator/src/task-execution.ts)은 worker 결과를 기록하고 `release()`로 Herdr 탭을 닫은 **다음** completion check를 실행한다. [Rust reducer](../../crates/loop-core/src/event/reducer.rs)는 검사 실패 시 새 `Ready` attempt 또는 attention으로 전이하므로, 현재 경로에서는 그 실패를 동일한 살아 있는 worker에게 되돌릴 수 없다. **가설:** 좁은 check를 worker가 살아 있을 때 실행하고 실패 영수증을 같은 Pi 세션에 전달해 제한된 수정 기회를 주면 새 worker 기동·문맥 재구성 비용을 줄일 수 있다. Rust의 독립 completion check는 최종 게이트로 다시 실행하고, scope와 retry budget을 지킨다. Herdr/Pi가 종료 전 재입력을 지원하는지 먼저 확인해야 한다. **검증:** 같은 실패 fixture에서 수정 완료 시간·모델 호출 수·파일 범위 위반·최종 검사 통과율을 기존 새-attempt 경로와 비교한다.

### P1 — 문맥·병렬 작업·TUI 체감 품질

9. **작고 관련된 코드 지도.** Rust/TS symbol과 bridge→generated consumer 관계를 색인해 첫 turn에는 필요한 것만 싣는다. Aider의 repo map처럼 토큰 예산을 제한하고 색인이 낡으면 직접 파일을 다시 읽는다. [Aider repo map](https://aider.chat/docs/repomap.html). **검증:** 탐색 tool call 수·잘못 선택한 파일·token 사용량·수정 성공률을 비교한다.
10. **파일 경계 규칙의 지연 로딩.** 전역에는 짧은 AGENTS 계약만 싣고 해당 경계의 파일에 닿을 때 Rust/codegen/UI 규칙을 추가한다. [OpenHands path rules](https://docs.openhands.dev/sdk/guides/skill). **검증:** 중요한 규칙 위반 없이 prompt 크기와 첫 worker 시작 지연이 줄어드는지 본다.
11. **worker 탐색과 선택을 Pi 안에서 끝내기.** Pi 위젯은 현재 task·run 식별자·상태를 짧게 표시하고, 선택하면 대응 Herdr 탭으로 가거나 transcript/diff를 확인한다. 완료 탭은 지금처럼 닫되 결과·근거는 durable run에서 계속 읽는다. [OpenCode child navigation](https://opencode.ai/docs/agents), [Claude teams TUI](https://code.claude.com/docs/en/agent-teams), [Pi extension UI](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md). **검증:** 여러 동시 worker 중 잘못된 탭을 고르지 않고, terminal 후 탭 누수가 없는지 TUI에서 확인한다.
12. **독립 작업만 동시 실행하고 변경은 안전하게 합치기.** Rust scope 충돌 검사를 유지한다. 같은 파일을 만질 가능성이 큰 작업에는 격리 checkout과 단일 integration owner를 실험한다. 실패·취소 변경을 사용자 소유 dirty tree에 자동 병합하지 않는다. [Claude teams conflicts](https://code.claude.com/docs/en/agent-teams), [OmO isolation](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/senpi-task.md). **검증:** 겹치는 파일/병행 dirty tree/worker 실패 fixture에서 데이터 손실이나 중복 병합이 없어야 한다.
13. **child 재개와 종료를 분리하기.** 완료 worker 탭은 닫는다는 사용자 선택을 유지한다. 재질문이나 실패 수정은 새 worker가 매번 원문 전체를 다시 읽는 대신, 검증된 요약·영수증 또는 보존된 Pi 세션으로 이어갈 수 있는지 비교한다. 세션 복원은 비밀정보·stale context·수명 관리를 포함해 평가한다. [OpenHands task resume](https://docs.openhands.dev/sdk/guides/task-tool-set), [OmO task revival](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/senpi-task.md). **검증:** 동일 버그의 2차 수정에서 시간·token·정답률을 비교한다.
14. **사용자 주의 요청을 결정이 필요한 경우로 한정.** 진행 알림은 Pi 위젯, 질문·승인·충돌·소진 실패는 Lead 대화에 남긴다. 팀원 메시지로 사용자의 승인을 대리하지 않는다. [Claude teams communication](https://code.claude.com/docs/en/agent-teams). **검증:** 장시간 작업에서 중요 결정 누락, 불필요 알림, 사용자 입력 후 재개 지연을 센다.

### Gajae-Code 후속에서 추가된 교차 과제

- **검증 대상 고정:** 누적 diff·변경된 허용 기준·검사 영수증을 동일한 소스 상태에 묶어, 검증 도중 다른 worker가 코드를 바꾸면 이전 검사 결과를 현재 코드의 증거로 오인하지 않는다. [Gajae-Code 검토 경계](https://github.com/Yeachan-Heo/gajae-code/blob/ec17cb15a3dae2d201752fb91297b0e181faf427/packages/coding-agent/src/defaults/gjc/skills/ultragoal/SKILL.md#L244-L304).
- **재조회 가능한 큰 출력:** 요약 전에 비밀정보를 제거한 원문을 안전하게 보관하고, Lead가 필요할 때 검사 출력·worker 결과를 다시 열게 한다. 원문 보존이 실패했다면 `artifact://` 참조를 만들어서는 안 된다. [Gajae-Code artifact](https://github.com/Yeachan-Heo/gajae-code/blob/ec17cb15a3dae2d201752fb91297b0e181faf427/docs/blob-artifact-architecture.md#L1-L30).
- **추가 worker의 실익:** worker별 시간·토큰·비용·변경 파일을 짧은 receipt로 남겨 위임으로 절약한 전체 시간과 비교한다. [Gajae-Code receipt](https://github.com/Yeachan-Heo/gajae-code/blob/ec17cb15a3dae2d201752fb91297b0e181faf427/packages/coding-agent/src/task/receipt.ts#L1-L64).

### P2 — 반복 작업과 운영 편의

15. **선택적 graph template.** bridge→codegen→소비자, UI→화면 검토, 버그 재현→수정→focused check 등 반복 흐름만 템플릿으로 제공한다. persona, skill, workflow를 같은 설정으로 섞지 않는다. [Goose roles/recipes](https://github.com/aaif-goose/goose/blob/main/documentation/docs/guides/context-engineering/custom-agents.md). **검증:** template가 실제 수정 시간을 줄이는지, 단일 작업에 불필요한 node를 늘리지 않는지 확인한다.
16. **비용·모델 선택의 근거 표시.** 작업 목적에 따른 모델 후보는 구성에서 고르고, 실제 선택한 provider/model·quota 실패·fallback 여부를 task 영수증에 남긴다. 읽기 전용 탐색에 더 작은 모델을 쓰는 것은 비용/시간 가설이며 품질 검증 후 채택한다. [OmO categories](https://github.com/code-yeongyu/oh-my-openagent/blob/dev/docs/guide/orchestration.md), [Claude subagents](https://code.claude.com/docs/en/sub-agents). **검증:** 같은 태스크 셋에서 시간·완료율·호출 비용을 함께 비교한다.
17. **checkpoint의 정확한 범위.** 외부 agent의 rewind UX는 편리하지만 shell·subagent 편집까지 되돌린다고 약속하면 위험하다. Claude Code도 그 범위를 제한한다. Loop는 event 재개와 실제 파일 변경 복구를 각각 명시하고, 되돌리기는 소유 파일·영수증 기준으로 설계한다. [Claude checkpoint limitations](https://code.claude.com/docs/en/checkpointing). **검증:** worker 중단·Lead 종료·Herdr 재시작 후 run 상태와 파일 변경을 각각 재구성한다.
18. **반복 오류·결정의 검증 가능한 기억(별개 Kage 참고).** [Kage memory 공식 가이드](https://kage-core.com/guide.html)는 기억을 근거 파일 경로와 내용 해시에 연결하고 파일 변경·삭제 시 stale로 판정해 recall에서 제외한다고 설명한다. **Loop 제안:** 반복되는 실패 원인과 중요한 설계 결정만 짧게 저장하고, 관련 소스가 바뀌면 다시 검증하기 전까지 worker 문맥에 넣지 않는다. Kage memory는 Gajae-Code와 별개다. **검증:** 오래된 지침이 잘못된 파일 수정을 유도하지 않는지, 재탐색 시간 절감과 오답률을 함께 비교한다.

## 먼저 할 실험

1. 같은 모델·설정·검사를 고정한 **4개 fixture**: 단일 수정, bridge/codegen 변경, 독립 작업 2개, 실행 중 기준 변경.
2. 각 fixture에 단일 worker 기준선과 현재 Pi Lead→Loop 경로를 반복 적용한다. `P50/P95` 지연, 성공률, 추가 지시 반영률, 429, task 수, token/비용을 함께 기록한다.
3. 위 결과에서 가장 긴 구간을 겨냥해 P0 항목을 하나씩 적용한다. 오프라인 fake 실행은 scheduler 회귀 증거로, 실제 Pi/Z.AI/Herdr 실행은 사용자 체감 증거로 분리한다.

이 문서는 기능 제안이다. 위 항목을 구현·벤치마크·실사용 검증한 결과로 읽지 않는다.
