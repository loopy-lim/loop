# Persona Briefing: Data-Science/ML Engineer & Site Reliability Engineer

- **Date:** 2026-09-22
- **Purpose:** Research deliverable for Loop's persona-driven development-analysis capability. Describes how data-science/ML engineers and SREs actually work — notebook-to-pipeline promotion, experiment tracking and evaluation gates, error budgets, incremental rollout and rollback drills, and runbooks — with observable patterns that can be encoded as workflow profiles (plan-first / spike-first / TDD-first and successors) and matched against Loop's own run traces.
- **Method:** Synthesis of primary public sources — the Google SRE book and workbook, the Google Cloud MLOps architecture guide, Netflix's tech blog, open-source tooling docs (MLflow, Metaflow), Microsoft's Team Data Science Process docs, a USENIX DiRT paper, PagerDuty's incident-response guide, and Wikimedia's public SRE runbooks. All links verified reachable (see Sources; the canonical Netflix Medium link serves 403 to scripted fetches but resolves in a browser).
- **Relation to prior briefings:** `bigtech-engineer.md` covers the shared trunk/review-gate culture, including several SRE-book chapters. This briefing focuses on the parts of the two personas that that briefing does not: the ML empirical loop (hypothesis → experiment → evidence → promotion) and the operational reliability loop (budget → drill → runbook). The two personas are deliberately paired: the ML engineer optimizes for iteration speed under uncertainty, the SRE for change control under risk. Their shared core is **evidence-gated promotion** — work earns advancement through measured evaluation, not through review alone.

## Who this persona is

**The data-science/ML engineer** works on problems where the correct behavior of the system is *unknown in advance* and must be discovered empirically. Progress is a cycle of hypothesis, experiment, and measurement; the natural unit of work is the *experiment run* (code + config + data version + metrics), not the commit. Output artifacts are models and pipelines whose quality can only be asserted by evaluation on held-out or live data. Tooling (notebooks, experiment trackers, registries) exists to make thousands of throwaway runs comparable and to freeze the survivors into reproducible production jobs.

**The site reliability engineer** owns a system whose failure is a matter of when, not if. The unit of work is the *risk-managed change*: every change ships behind a quantitative reliability target, moves through measured rollout stages, and has a rehearsed, written recovery path. Tooling (SLOs, error budgets, load tests, runbooks) exists to make failure boring — precomputed decisions instead of improvisation.

## 1. Notebook-to-pipeline promotion: scratch runs graduate or die

- Exploration happens in **notebooks**: fast, stateful, interactive, optimized for asking questions. The public sources are unanimous that this is where the work *starts* — and equally unanimous that notebooks are not where work *ends*. Netflix's notebook platform team built the missing bridge explicitly: make the same notebook that a person explores with schedulable as a production job, so that "notebook-first" and "production-first" are two stages of one artifact's life rather than a rewrite boundary ([Scheduling Notebooks at Netflix]).
- The standard promotion path is **notebook → refactored module → parameterized pipeline job**: extract logic into functions, version the inputs (data snapshot, config, seed), wrap in a scheduler/runner (Airflow, Metaflow, Dagster, Kubeflow), and let the pipeline become the canonical version while the notebook stays a dev harness. Metaflow's docs state the goal directly: the same code the scientist runs locally should scale to production without translation ([Metaflow — What is Metaflow?]).
- Google's MLOps guide frames promotion as a **pipeline deployment**: a "training pipeline" that can be re-run on new data and a "serving pipeline" that deploys only after validation gates pass; the manual-notebook stage is CT (continuous training) level 0, explicitly labeled a starting point to grow out of, not a destination ([MLOps: Continuous delivery and automation pipelines in ML]).
- Promotion is **evidence-gated**: an artifact moves forward only after evaluation (see §2), and a failed gate sends it back to the notebook, not to production. The pipeline stage is where reproducibility is enforced — pinned data versions, fixed environments, deterministic entry points — because a run you cannot re-create is a result you cannot trust ([Hidden Technical Debt in ML Systems]).
- The anti-pattern is documented as debt: glue code, tangled "path-to-production" logic, and dead experimental branches in notebooks make the gap between lab and production the single largest source of ML maintenance cost ([Hidden Technical Debt in ML Systems]).

## 2. Experiment tracking and evaluation gates: every run is comparable evidence

- The working habit is **experiment-per-change**: each run records its code version, hyperparameters/config, data version, and resulting metrics in a tracker (MLflow Tracking is the open-source reference; W&B, Vertex, SageMaker follow the same shape). The tracker's value is *comparability* — "did that change actually help?" is answered by querying runs, not by memory ([MLflow Tracking docs]).
- Microsoft's Team Data Science Process formalizes the loop as named lifecycle stages (business understanding → data acquisition → modeling → **deployment**, with iteration between them) and explicitly prescribes reproducibility: versioned data, versioned code, recorded metrics, so any result can be re-derived ([Team Data Science Process overview]).
- **Evaluation gates** decide promotion. Google's MLOps maturity model requires automated validation before deployment: metric thresholds on held-out data, model-behavior comparison against the incumbent, and only-then registry promotion and rollout ([MLOps: Continuous delivery and automation pipelines in ML]). Offline metrics are necessary but not sufficient — the final gate is an online controlled experiment; Booking.com's engineers reported that for their models, offline improvements frequently failed to translate, so the A/B test, not the offline score, is the gate that counts in the end (this source was consulted for context but its public blog link 404s; the offline-vs-online gap is corroborated by [MLOps] and [Hidden Technical Debt]).
- The gate vocabulary is deliberately **quantitative**: "accuracy ≥ X," "regression ≤ Y%," "latency p99 ≤ Z." A gate expressed as a number can be automated, and automated gates are what make fast iteration safe — the pipeline promotes itself when evidence passes and refuses when it does not ([MLOps]).
- Rolling back a promoted model is a normal, expected outcome, not an exception: registry systems model this directly with stage transitions (staging → production → archived) and versioned artifacts, so "revert to the previous version" is a lookup, not a rebuild ([MLflow Tracking docs]).

## 3. Error budgets: reliability as a spendable quantity

- The SRE starting point is that **100% reliability is the wrong target**: SRE Book Ch. 3 introduces the error budget as 1 − SLO — the tolerated amount of failure that the product *chooses* to spend ([Embracing Risk]). Google Cloud's fundamentals doc makes the operational chain explicit: pick SLIs (user-centric indicators), set SLOs against them, and treat the remaining error allowance as a budget ([SRE fundamentals: SLIs, SLAs and SLOs]).
- The budget is not a dashboard; it is a **policy**. The SRE Workbook's Implementing SLOs chapter requires a written error-budget policy: what happens when the budget is exhausted — feature launches pause, releases slow down, reliability work takes priority — and who has authority to override. Without the policy, SLOs are decoration ([Implementing SLOs]).
- Because the budget is quantitative, it arbitrates the classic tension between the two halves of this briefing: ML/product engineers want to ship experiments; SREs want change control. The budget converts that argument from a tug-of-war into arithmetic — shipping is allowed while budget remains, and the same rule binds everyone ([Embracing Risk], [Implementing SLOs]).
- For Loop's purposes, note the shape: a *numeric completion contract* plus a *pre-agreed consequence* when the contract fails. No judgment call at gate time — the policy was decided in advance, when nobody was mid-firefight.

## 4. Incremental rollout and rollback drills: rehearse the failure path

- Changes reach production through **measured stages** — canary slice, then growing tiers — with health signals compared between canary and baseline at each stage, and automatic halt/rollback on regression. (The big-tech briefing covers this mechanism in depth via Amazon's Builders' Library and Netflix Kayenta; here the emphasis is the SRE-specific half: proving rollback works *before* you need it.)
- Google institutionalized this as **DiRT** (Disaster Recovery for IT / Disaster Recovery Testing): scheduled exercises that deliberately break production — take out datacenters, kill dependencies, simulate overload — to verify that recovery procedures, backups, and failovers actually function. The published account reports initial manual executions ("Game Days") and later automation, and is explicit that untested recovery is imagined recovery ([Introducing DiRT]).
- The SRE Book's Emergency Response chapter describes the same practice as the **"Test Emergency"** or Unusual Internal Incident: a staged, unplanned-seeming emergency injected on purpose, with observers grading the on-call's response against the runbook, so that response skill is trained and procedure gaps are found without a real outage ([Emergency Response]).
- Chaos engineering is the ecosystem-level generalization: hypothesize steady state, inject real-world failure, run the experiment in stages (start small), and minimize blast radius — the discipline's stated principles ([Principles of Chaos]). The common structure across DiRT, Test Emergencies, and chaos experiments: **the failure path is a scheduled, observable, graded task**, never an implied one.
- Rollback occupies a first-class position in the workflow: the drill's success criterion is "we returned to steady state via the documented path," so the rollback procedure is exercised with the same rigor as the deploy procedure.

## 5. Runbooks: precomputed decisions for the worst day

- A **runbook** is the written decision tree for a known failure mode: detection query, severity definition, step-by-step diagnosis, mitigation, escalation contacts, and verification that service is restored. Wikimedia's SRE org maintains runbooks as public documents and — crucially for pattern-matching — links them *from the alerts that fire*, so the page a responder sees names the procedure ([Wikimedia SRE runbooks]). PagerDuty's incident-response guide standardizes the same artifact set (severity levels, escalation paths, prepared responders) and treats documentation as an input to response speed, not an afterthought ([PagerDuty Incident Response]).
- The design insight is that response quality under stress is too important to leave to improvisation: the expert's judgment is *encoded in advance* as steps, so a responder with less experience can execute it. Emergency Response makes this a training loop: run the drill, grade against the runbook, fix the runbook ([Emergency Response]).
- Runbooks and error budgets close the loop together: an incident that exhausts budget produces a postmortem whose action items include runbook updates and alert fixes — the same "failure produces tracked documents" pattern the big-tech briefing found, but here pointed at operational procedures rather than code review.
- The runbook is also the SRE answer to the ML engineer's reproducibility requirement, seen from the other side: both personas refuse to let critical knowledge live only in someone's head or someone's notebook scratch cells.

## Observable patterns (for trace/profile matching)

1. **Experiment-per-change with recorded config:** every attempt runs with pinned inputs (data version, config, seed) and produces measured results. In a trace: many short implement→verify pairs, each emitting an evaluation artifact; high iteration count upstream of any promotion.
2. **Evidence-gated promotion (diamond shape):** an artifact advances only through an explicit evaluation gate, and a failed gate routes *back* to exploration rather than forward. In a trace: verification/analysis node whose outcome gates a promotion/integration node — a diamond with a defined failure edge, not a straight line to done.
3. **One canonical pipeline, many throwaway branches:** scratch work diverges freely, but the production path is a single frozen, versioned pipeline that survivors join. In a trace: several parallel spike/exploration nodes converging into exactly one serialized integration node.
4. **Numeric completion contracts with pre-agreed consequences:** gates are thresholds ("metric ≥ X") decided in advance, and budget exhaustion flips priorities automatically. In a trace: completion checks as numeric predicates; a policy-driven re-route (e.g., fast-to-strong escalation or priority flip) that fires on exhaustion without human judgment.
5. **Rehearsed failure paths:** rollback/recovery is scheduled and exercised as a first-class task, not implied by success paths. In a trace: explicit rollback/diagnosis tasks present in the DAG (and occasionally executed) even when the happy path succeeds.
6. **Runbook as precomputed decision tree:** response to known failure modes instantiates a stored procedure instead of improvising. In a trace: task templates/playbooks that a dispatcher expands into concrete nodes, rather than free-form decisions made mid-run.
7. **Docs are inputs, linked from triggers:** procedures (runbooks, eval specs) are referenced at the moment of use — an alert links its runbook; a registry promotion links its eval criteria. In a trace: task payloads carry references to governing documents/checklists rather than re-deriving them.

## Mapping to Loop workflow profiles

- **Spike-first** ≈ the notebook/exploration stage: divergent parallel attempts, cheap, expected to mostly die; value is learning, output is a findings artifact.
- **TDD-first / eval-gate-first** ≈ the evaluation gate: define the quantitative check *before* implementation, let the check decide promotion; the ML persona's core discipline.
- **Plan-first** ≈ the SRE policy layer: error-budget policy, runbook, and drill schedule are all decisions made *before* execution so that in-flight behavior is mechanical, not judgment-based.
- The two-persona pairing is the tension Loop's benchmark should preserve: profiles are not better/worse but trade iteration speed (ML side) against change safety (SRE side), and the error budget is the existing industry mechanism for making that trade explicit and numeric.

## Tensions and caveats

- **The public narrative idealizes.** Hidden Technical Debt exists precisely because most real ML work does *not* cleanly promote notebooks to pipelines; in practice much production ML is glue code around notebooks, and offline gates are often skipped. The patterns above are the discipline the sources prescribe, not a census of behavior.
- **Evaluation gates need ground truth.** The whole ML loop assumes you can measure "better." For open-ended or one-shot work (much of what Loop runs), no held-out set exists, so "eval-gate-first" maps to proxy checks (tests, static analysis, contract checks) rather than true evaluation.
- **Scale mismatch.** SRE practices come from organizations with fleets of servers and staffed rotations; a single-agent run has neither fleets nor rotations. The transferable content is the *structure* (numeric budgets, rehearsed failure paths, precomputed procedures), not the infrastructure.
- **Two sub-personas in tension.** The ML engineer's bias (explore fast, promote evidence) and the SRE's bias (change slowly, rehearse failure) pull in opposite directions; sources from each camp advocate their own default. Cross-field synthesis should treat them as complementary phases of one promotion loop, not competing methodologies.
- **Overlapping sources with the big-tech briefing.** SRE-book chapters cited there (postmortem culture, release engineering) were excluded here where redundant; this briefing adds the workbook, DiRT, emergency-response, and runbook literature instead.
