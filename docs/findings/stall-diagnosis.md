# Running-task stall diagnosis

## Scope and conclusion

A task can remain `running` indefinitely while the coordinator process and lease heartbeat remain alive. The core reducer has no elapsed-time transition/watchdog: `WorkerStarted` transitions a ready task to running (`crates/loop-core/src/event/reducer.rs:286-292`), and terminal state changes depend on later result/verification/reconciliation events. The coordinator polls but does not impose a task deadline (`packages/orchestrator/src/coordinator.ts:298-320, 511-512`).

## Hang paths

1. **Worker result never settles (including dead/unreported worker).** After startup, `executeTask` awaits `untilAborted(provider.result(handle.id), signal)` (`packages/orchestrator/src/task-execution.ts:250`). This races only the result promise against explicit abort (`:525-540`); no worker-result deadline exists. A worker process that exits without the adapter settling/rejecting `result`, or a hung model stream, leaves the execution unsettled. The coordinator only removes settled executions and keeps polling (`packages/orchestrator/src/coordinator.ts:315-320, 511-512`); its heartbeat continues renewing ownership (`:234-254`). Thus no restart/recovery path runs while the same owner remains alive.

2. **Completion check process/result hangs despite configured timeout.** Checks enter `verifier.verify` after a successful worker result (`packages/orchestrator/src/task-execution.ts:336-340`). `NodeCompletionRunner` starts a timeout that calls `process.cancel()`, but then awaits `Promise.race([process.result, stopFailure])` and subsequently `await stopping` (`packages/orchestrator/src/completion.ts:88-113`). If cancellation hangs or the process runner's result does not settle after cancellation, verification remains pending; `recordVerification` is not reached (`packages/orchestrator/src/task-execution.ts:466-473`). A check timeout therefore bounds the request to stop the process, not completion of cancellation/result settlement. Cancellation signal follows the same stop path.

3. **Lifecycle and control calls that never resolve.** `LifecycleTimeout` is only used by `bounded`, currently for provider release (`packages/orchestrator/src/task-execution.ts:132-145, 542-556`), not `provider.result`, `provider.cancel`, or the normal model stream. Cancellation branch awaits `provider.cancel` before recording stopped (`:251-255`); catch/finally also await cancel/release and control writes (`:489-511, 512-522`). If any of those promises never settles, task execution can likewise remain pending. `provider.repair` also uses `untilAborted` without a deadline (`:436-447`).

4. **Provider routing/capability and preparation stalls.** Initial route lookup is bounded by `selectWhileActive`'s 30-second deadline (`packages/orchestrator/src/coordinator.ts:549-570`), but preceding run-plan/snapshot/context/mailbox/control awaits and source capture have no local timeout (`:190-191, 257-258, 337-362`; `packages/orchestrator/src/task-execution.ts:182-184`). These can stall the dispatcher before it reaches failure/attention handling. Fallback route lookup uses `#routeFor` (`coordinator.ts:428-464`) and depends on its own route implementation; unlike the initial `selectWhileActive` shown above, this call site has no explicit deadline.

5. **Unknown startup outcome.** `startup()` bounds waiting for provider.start to 30 seconds (`packages/orchestrator/src/task-execution.ts:558-573`). Expiry throws `StartupUncertain`; catch requests failure attention but deliberately does not mark worker stopped/failed because the side-effect outcome is unknown (`:210-221, 478-486`). The task therefore remains running/owned until explicit reconciliation. Late-start cleanup is fire-and-forget and swallowed on rejection (`:214-219`). This is bounded detection, not automatic terminal transition.

## Existing timeout/watchdog mechanisms and exact gaps

- **LifecycleTimeout:** 5-second `bounded` timeout only on `provider.release` (`task-execution.ts:132-145, 545-556`). No timeout around worker result/stream, cancel, repair, or persistence/control calls. Release timeout itself requests attention and exits via `CleanupFailed`; it does not provide a general worker watchdog.
- **Worker startup timeout:** 30 seconds (`task-execution.ts:558-573`). Timeout produces `StartupUncertain` attention (`:478-486`), not failed state, pending safe reconciliation.
- **Completion-check timeout:** task contract carries `timeout_ms`, default 120,000 ms (`crates/loop-core/src/task/contract.rs:49-69`); verifier validates it and runner schedules cancellation (`packages/orchestrator/src/completion.ts:42-60, 88-113`). Gap: stop/result settlement has no second bounded deadline.
- **Execution lease heartbeat:** claim uses TTL 5,000 ms and renews every 1,000 ms (`packages/orchestrator/src/coordinator.ts:199-201, 234-254`); bridge delegates claim/renew to store (`crates/loop-bridge/src/execution.rs:667-682`). It detects owner loss, not worker/task inactivity. A live coordinator stuck awaiting a worker continues refreshing the lease, preventing another coordinator from taking over. On owner restart, recovery requests attention for persisted active workers/verifying tasks (`coordinator.ts:256-283`), but this requires a new owner and does not detect a hung task within a live owner.
- **No durable progress signal / age-based watchdog:** worker output activity may be recorded at most once per second, but only when raw activity is enabled, and is not a worker lifecycle deadline (`task-execution.ts:234-249`). Worker start/result are durable lifecycle events; absent result leaves no persisted last-progress timestamp. No policy in the requested core task/policy paths expires running tasks by elapsed time. Open attention also has no age-based escalation in these paths.

## Implication for dependent implementation

Add durable progress timestamps through Rust domain/event/store/bridge so status can distinguish recently active from stale; emit progress from orchestrator for meaningful worker activity (and verification stages). Add a coordinator watchdog based on last progress with explicit policy for safe cancellation and unknown worker outcome; do not treat lease renewal as worker health. Surface stale-running and open-attention age as derived status, while retaining explicit reconciliation when process termination cannot be proven. Ensure completion-runner timeout bounds cancellation settlement as well as command execution.
