# 실행을 관찰하고 개입하기

Loop는 저장된 작업 그래프를 별도의 실행 프로세스에서 진행한다. Pi 화면과 CLI는 상태를 읽고 제어 요청을 저장한다. 화면을 닫거나 관찰 연결이 끊겨도 실행 프로세스와 작업은 계속된다.

| 목적 | 명령 |
| --- | --- |
| 저장된 실행 찾기 | `loop runs` |
| 현재 작업과 진행 상황 | `loop status <run-id>` |
| 의존성, 범위, 대기 이유 | `loop graph <run-id>` |
| 상태 변화를 계속 관찰 | `loop watch <run-id>` |
| 작업 결과와 검증 기록 | `loop task <run-id> <task-id> --json` |
| 실행 중인 작업을 마친 뒤 일시정지 | `loop pause <run-id>` |
| 다음 작업·재시도에 지침 반영 | `loop steer <run-id> <task-id 또는 all> <message>` |
| 질문·승인·실패에 응답 | `loop resolve <run-id> <attention-id> <approved 또는 rejected 또는 retry 또는 cancel 또는 답변>` |
| 저장된 그래프에서 계속 | `loop resume <run-id>` |
| 작업과 검증을 실제로 중단 | `loop cancel <run-id>` |

Pi에서는 `/loop status`, `graph`, `workers`, `attention`, `runs`, `task`, `pause`, `resume`, `steer`, `resolve`, `cancel`을 사용할 수 있다. 지속 관찰과 중단 확인은 CLI의 `watch`, `reconcile`을 사용한다. 기본 상태는 8줄, 주의 요청은 6줄, 작업별 발견 사항은 5줄 안으로 표시한다. 전체 그래프와 기록은 CLI의 `--json`으로 확인한다.

## 개입 시점과 복구

`pause`는 새 작업 배정을 멈추고 이미 시작한 작업과 검증을 마친다. `steer`는 지침을 영구 저장하여 이후에 시작하거나 재시도하는 작업에 전달한다. 진행 중인 모델 호출의 프롬프트를 소급해서 변경하지 않는다. 즉시 멈춰야 한다면 `cancel`을 사용한다. 취소가 요청된 상태와 실제 작업이 종료된 상태는 구분된다.

승인 대기 항목은 `resume`만으로 해제되지 않는다. 열린 항목을 각각 해결한 뒤 재개해야 한다. 승인 항목에는 명시적인 `approved`가 필요하며, `rejected`는 해당 실행을 취소한다. 완료되거나 취소된 실행은 재개할 수 없다. 다시 실행하려면 새 실행을 만든다.

화면 종료와 실행 프로세스 자체의 장애는 다르다. 실행 프로세스가 비정상 종료되어 이전 작업의 상태를 확신할 수 없으면 중복 실행을 막고 확인 요청을 남긴다. 이전 작업 및 검증 프로세스가 모두 멈춘 것을 확인한 뒤 `loop reconcile <run-id> <task-id> stopped`를 실행하고 재개한다. 취소 중이던 실행은 마지막 중단 확인 후 취소를 마무리한다. 실행 소유권이 아직 유효하면 이 조작은 거절된다. 단순한 관찰 연결 종료에는 이 절차가 필요 없다.

## 병렬 실행과 결과 전달

작업은 의존성과 읽기·쓰기 범위를 선언한다. 독립 작업은 설정한 동시 실행 수 안에서 병렬로 진행하며 검증도 같은 한도에 포함한다. 쓰기와 읽기가 충돌하거나 쓰기 범위가 겹치는 작업은 동시에 배정하지 않는다. 결정·통합 작업은 직렬화한다. 범위는 프로젝트 내부의 상대 경로이며 일반 glob은 보수적으로 충돌 판정한다. 이는 스케줄러의 소유 범위 계약이며 운영체제 수준의 파일 접근 격리는 아니다.

각 작업에는 원래 요청, 현재 지침, 직접 의존하는 완료 작업의 결과, 선언한 범위, 완료 조건, 이전 실패와 검증 기록을 전달한다. 작업자의 성공 보고 이후에도 완료 조건의 명령이 통과해야 작업이 완료된다. 상태·요약·기록에 포함되는 일반적인 인증 토큰 패턴은 저장 전에 가린다.

## 실패 재시도와 terminal 종결

재시도 가능한 timeout·일시적 process/environment 실패만 task의 `maxAttempts` 예산 안에서 재시도한다. 예산이 소진되면 질문을 만들지 않고 task와 run을 terminal `Failed`로 종결하며, 실패 task의 후손은 `Blocked`로 전파한다. 의존하지 않는 branch는 계속 실행한다. decision·integration 작업이 실패하면 부분 결과를 채택하지 않고 run을 실패로 닫는다. 다만 프로세스 생존 여부가 불명확해 재시도가 중복 부작용을 만들 수 있는 경우처럼 terminal 상태를 안전하게 확정할 수 없을 때는 attention과 수동 reconcile을 유지한다.

deterministic assertion 같은 completion-check 실패는 같은 명령을 재시도하거나 compute class를 승격하지 않으며 첫 실패를 terminal `Failed`로 기록한다. 실패한 check를 worker 성공 보고로 대체하거나 `Done`으로 승격하지 않는다.

모델 라우팅에서는 `config/models.toml`의 strong 후보 `zai/glm-5.3-flash:high`를 우선해, 검증 실패로 compute가 승격될 때 openai-codex quota가 소모되지 않도록 한다.

이 동작은 fake/offline 시나리오와 자동 회귀 검사로 검증한다. 실제 인증 provider·유료 모델 호출·장시간 운영 환경의 live evidence는 별도이며, 확보되지 않은 경우 공급자별 오류 매핑과 실제 quota fallback까지 검증된 것으로 해석하지 않는다.

## 저장 형식과 빌드

이벤트 기록을 보존하며 현재 상태 캐시를 같은 저장 트랜잭션에서 갱신한다. 캐시가 없거나 읽을 수 없으면 이벤트를 재생한다. 기존 전역 식별자 테이블은 실행별 복합 식별자로 자동 이전한다. 실행별 소유권 임대가 중복 배정을 막고, 작업 상태를 기록하는 트랜잭션에서도 소유권을 확인하여 이전 실행 프로세스의 늦은 결과를 거절한다.

Jev 실행 경로는 제거했다. Rustra는 공개된 버전으로 고정하며 인접한 Rustra 소스 저장소가 필요하지 않다. 생성기의 두 알려진 문제는 `scripts/rustra-codegen.ts`에서 재현 가능한 방식으로 보정한다. Rust 계약을 수정한 뒤 `bun run codegen`으로 생성하고 `bun run check`로 검증한다.

실제 공급자 인증, 유료 모델 실행, Herdr 화면 조작의 실제 환경 검증은 자동 검사와 별개다. 자동 검사는 가짜 공급자와 로컬 프로세스로 실행된다.
