# herdr 내용 revision 합성 + 에이전트 패인 출력 감시 — 채팅 실시간 갱신

- **태스크:** 실시간 갱신 진단 후속 (2026-10-21, loop-mobile 채팅 화면이 에이전트 스트리밍 중 갱신되지 않는 문제)
- **상태:** 결정됨
- **작성일:** 2026-10-21
- **선행 결정과의 관계(확장 채택):**
  - [`2026-xx-terminal-mirror.md`](2026-xx-terminal-mirror.md) **D2가 확장점으로 남긴 매처 구독(S2)**을 이 결정이 채택한다 — "지연 요구가 커지면 후속 결정으로 승격한다"의 그 후속 결정이다. D2의 리비전 폴링(S1) 채택 자체는 유지되며, 폴링이 **무엇을 변경 훅으로 쓰는지**가 본 결정에서 바뀐다.
- **입력:** 라이브 프로브(2026-10-21, 설치된 herdr 0.9.5 / 프로토콜 22 — 스크래치 워크스페이스에서 출력 발생 후 `session.snapshot`·`pane.read`·`pane.output_matched` 관측), `docs/research/simulator-showcase/v3/evidence.md` D-c, `packages/gateway/src/herdr-pane-source.ts`, `packages/gateway/src/herdr-state.ts`, `packages/gateway/src/pane-mirror.ts`

## 1. 배경

앱의 대화 화면은 `herdr_state` 프레임의 `pane.revision`이 바뀔 때만 대화를 다시 가져온다. 그런데 라이브 검증 결과 **herdr의 revision 카운터는 변경 훅으로 못 쓴다**: `pane.read`의 revision은 패인 수명 내내 0으로 동결하고, `session.snapshot`의 패인 revision은 초기 렌더 직후 동결하며(프로브에서 출력이 흐르는 5초 동안 3으로 고정, 텍스트 길이는 1097→1099로 변화) 값이 내려가기도 했다(18/15/10 → 3/3/3). 시뮬레이터 쇼케이스 v3가 같은 증상을 기록해 두었다(evidence D-c). 결과적으로 10초 안전망 폴링과 에이전트 상태 전이 이벤트만으로는 스트리밍 중 대화가 갱신되지 않았고, 같은 이유로 pane 미러의 revision 디듀도 첫 프레임 이후 정체된다.

## 2. 결정 (한 단락)

게이트웨이가 **텍스트 비교로 합성한 단조 revision**을 모든 pane 읽기 경로에 부여한다(`SyntheticPaneRevisions` — 동일 텍스트면 유지, 변하면 클라이언트 전역 시퀀스에서 다음 값을 배정; 시뮬레이터 쇼케이스 D-c에서 검증된 기법). 격리 축은 둘이다: 관찰 스트림별(미러 피드 / 상태 뷰+pane 읽기 루트)로 독립 표본을 두고, **같은 패인이라도 읽기 창이 다르면 별도 스트림**으로 키잉한다(모니터의 소형 text 테일 vs 루트의 넓은 ansi 창 — 같은 내용이라 텍스트가 다르므로, 창을 섞으면 서로를 계속 bump하는 무한 refetch 루프가 된다). 상태 모니터는 리프레시마다 **에이전트 패인만** 소형 테일 read(lines 12)로 이 합성 revision을 뷰에 심고, 읽기 실패 시 마지막 적용값을 유지하며, 안전망 폴링을 10s→**1s**로 조인다. 동시에 D2가 예약한 **매처 구독을 에이전트 패인에 한해 채택**한다 — `pane.output_matched`(모든 줄 매칭 regex `.`, `lines: 1` 최소 창)를 구독해 출력 도착 자체를 리프레시 트리거로 쓴다(coalesce 200ms 상한). 리프레시가 감시 시그니처(패인 집합×에이전트 여부)의 변화를 보면 피드를 재열어 출력 감시가 패인 집합을 따라가게 한다. 앱·wire 계약은 그대로다: 기존 `herdr_state` 프레임의 `pane.revision`이 이제 실제 내용 변화를 추적하므로 앱의 refetch 훅이 스트리밍 중에도 맞물리고, 프로토콜 codegen 변경은 없다. 앱은 revision을 **10진 수치로** 비교해야 한다("9"→"10" 경계 — 본 결정이 카운터를 실제로 움직이게 하며, 사전식 비교는 이 경계에서 읽기를 유실한다).

### D1. 변경 훅 — 합성 revision, herdr 카운터 기각

- **채택:** `herdr-pane-source.ts`의 모든 `pane.read` 소비 경로(관찰 포트 + 표면 클라이언트)가 텍스트 비교 합성 revision을 내보낸다. 키는 **패인 × 읽기 창**(lines·source·format)이고 카운터는 클라이언트 전역 시퀀스에서 배정한다 — 각 스트림에서 단조이며, 표본 상한 초과로 항목이 쫓겨나도 재시드 값이 이미 발급한 모든 값보다 크므로 소비자의 낡은 관찰값이 실제 변화를 가리지 못한다. herdr의 카운터는 응답 형태 검증(드리프트 게이트)에만 쓰고 값은 버린다.
- **기각 — herdr revision 신뢰(현상 유지):** 라이브 증거가 반증했다(배경 참조). 폴링을 촘촘히 해도 뷰 비교가 변화를 못 보면 version이 오르지 않는다.
- **기각 — 창 무시 단일 표본:** 모니터 테일(lines 12·text)과 읽기 루트(넓은 창·ansi)는 같은 내용에 대해 다른 텍스트를 받는다(ANSI 이스케이프, 창 길이). 하나의 표본을 섞어 쓰면 읽기마다 텍스트가 번갈아 바뀌어 카운터가 계속 오르는 **무한 refetch 루프**가 된다 — 창별 키잉이 필수다.
- **기각 — 이벤트의 `read` 페이로드를 뷰 원천으로:** `pane.output_matched` 이벤트가 실어 오는 `PaneReadResult`의 revision도 0으로 동결했다(라이브 확인). 이벤트는 트리거로만 쓰고 내용은 스냅샷+테일 read가 단일 원천으로 답한다.

### D2. 감시 범위 — 에이전트 패인 한정

- **채택:** 테일 read와 출력 구독은 `agent !== null` 패인에만 적용한다. 일반 셸 패인의 프롬프트 재렌더는 대화 갱신과 무관하고 이벤트·요청 폭발의 주범이다. 출력 구독 파라미터는 `lines: 1`로 최소화한다 — 필요한 것은 "출력이 있었다"는 신호뿐이다.
- **기각 — 전 패인 감시:** 위와 같다. 비에이전트 패인의 변화가 상태 뷰에 필요해지면 그때 확장한다.

### D3. 지연·비용 한도

- **빠른 경로:** 출력 줄 → `pane.output_matched` 푸시 → 모니터 리프레시(coalesce 200ms) → 테일 read → version 상승 → 앱 refetch. 실측 목표 수백 ms.
- **바닥:** 1s 안전망 폴링 — 모든 이벤트가 유실되어도 최악 ~1s+ε에 수렴한다.
- **비용:** 리프레시당 `session.snapshot` 1회 + **에이전트 패인 수에 비례한** 소형 테일 read 1회/패인(coalesce로 리프레시 자체는 초당 최대 5회). 유닉스 소켓 로컬 호출이라 통상적 에이전트 수(한 자릿수)에서 수용 범위다 — 패인 수십 규모가 필요해지면 테일 read 상한을 후속으로 둔다.
- **합성 카운터의 정직성:** 값은 클라이언트 전역 시퀀스에서 배정되므로 herdr 값과 수렴하지 않는다. 계약은 "같은 패인×창 스트림 안에서 단조 증가하는 변경 훅"이며 절대값 의미는 없다 — 이를 본 문서와 어댑터 주석에 명시한다.

### D4. 앱 변경 없음

- **채택:** 앱은 이미 `pane.revision` 변화로 대화를 다시 가져온다(rebuild brief §7의 구조적 데이터 부가 규칙). wire 필드 의미가 "실제 변화를 추적하는 단조 훅"으로 정정될 뿐 형태는 그대로라 앱 수정·codegen은 없다. 앱 쪽 주기 폴링은 중복이므로 도입하지 않는다.

## 3. 검증

- `packages/gateway/test/herdr-surface.test.ts`: 합성 revision이 상태 뷰·읽기 루트·관찰 포트 세 표면에서 단조 유지되는 것, 내용 변화만 version을 올리는 것, `output_matched` 푸시가 폴링 없이 수렴하는 것, 출력 구독이 에이전트 패인에만 붙는 것(파라미터 고정: regex `.`, `lines: 1`).
- 라이브 재검증: 게이트웨이 재시작 후 에이전트 스트리밍 중 폰 채팅 화면이 턴을 수 초 내 갱신하는 것(수동).

## 4. 리스크

- 스트리밍 중 version 상승 빈도가 높아 앱의 refetch가 최대 ~5회/초까지 늘 수 있다 — 읽기 2회(readPane+conversation)로 경미하나 체감 부하가 보이면 coalesce를 늘려 조율한다(파라미터 1개).
- 합성 표본 상한(128 항목, 패인×창) 초과 시 가장 오래된 항목이 쫓겨나지만 카운터는 전역 시퀀스에서 계속 배정되므로 낡은 관찰값과 충돌하지 않는다 — 재시드 블립은 없다.
- herdr 장애로 테일 read가 반복 실패하는 동안 에이전트 패인 revision은 마지막 적용값에 동결된다(스냅샷 카운터로 되돌리지 않음) — 뷰 진동 없이 수렴하며, 실패 구간의 내용 변화는 다음 성공 read에서 한 번에 반영된다.
