# Agent quality and nightly continuation

The Lead now submits `{tasks, criteria}`. Every task requirement has one explicit criterion that names the check IDs intended to prove it. The bridge remains the durable validator; the Lead rejects omissions before creating a run. A bounded quick run supplies the same mapping through `acceptance`. A later task supplies `{task, criteria}` atomically. The contract cannot prove that a chosen test truly exercises the behavior, so the Lead's final review still compares criteria with the original user request.

Plans with more than one implementation task require an integration task downstream of every implementation task. Its criterion and checks run against the combined result. The worker brief keeps intent, exact scopes, requirements, checks, guidance, and instructions ahead of supporting receipts; if that essential contract exceeds its prompt budget, dispatch fails visibly instead of silently truncating it.

`loop benchmark agents <manifest.json>` compares configured providers on the same committed Git source. Each trial uses a separate clone and the same task graph and criteria, with the registry pinned to one provider. It reports goal criteria, scope observations, retries, attention, elapsed time, and the persisted trace. Actual billing is explicitly `costMeasured: false`; no model call is required by the test suite. The manifest must name at least two provider IDs and a clean Git repository root. Candidate IDs are `<provider>:<model-id>` from the configured registry. Repeated trials remain necessary before making a routing policy change.

The nightly continuation is a macOS LaunchAgent at 02:00 local time. It runs `loop nightly --execute --json` once, with no immediate install-time run. Only active runs with no live lease, in-flight worker, verification, or open attention are launched. Ready work continues; all-done or stalled graphs receive one owner pass so the durable state can complete or raise attention. User-paused, attention, terminal, and ambiguous runs are skipped. It does not invent work from Git changes or resolve attention on behalf of the user. The launcher uses existing CLI authentication and never stores credentials in the plist or logs them.

Operators can inspect with `loop nightly --dry-run --json`, use `bash scripts/nightly-launchd-install.sh status`, or remove the schedule with `bash scripts/nightly-launchd-install.sh uninstall`. The plist is stored at `~/Library/LaunchAgents/kr.ll3.loop.nightly.plist`; the log is `~/.loop/nightly/nightly.log`.
